# Garden Areas ("Platser") with Periodic Maintenance

Date: 2026-08-26
Status: Approved design, ready for implementation planning

## Summary

Add a new first-class place under a garden — a `GardenArea`, labelled
**Plats/Platser** in the UI — for parts of the garden that are not growing
beds but still need work: gravel walkways that need weeding, lawns that need
mowing, hedges that need pruning.

Alongside it, add a recurring-maintenance engine: a `maintenance_rule` says
"weed this walkway every 21 days between April 1 and October 15". A daily job
turns due rules into ordinary `ScheduledTask` rows, so maintenance appears in
the task list, on the dashboard, and in the Android task flows with no
parallel UI.

Rules attach to **beds as well as areas**. Bed maintenance today is entirely
hand-made; the same engine makes it periodic.

## Motivation

`ScheduledTask` already supports bed-scoped maintenance (`WATER`,
`FERTILIZE`, `WEED`) and free-form `TODO` tasks, but every one of those rows
is created by hand. Nothing in the system repeats. `SuccessionSchedule` is the
only interval-based generator and it is sowing-specific.

Meanwhile there is nowhere to put a gravel path at all. It is not a bed, it
grows nothing, and the only way to remember to weed it is a `TODO` retyped
every three weeks.

## Decisions

These were settled during brainstorming and are not open in the plan.

| Decision | Choice |
|---|---|
| Shape of the concept | A full place, sibling of `Bed` under `Garden`: own record, photos, event history, notes |
| Code name | `GardenArea` (`garden_area`). UI label stays "Plats/Platser" |
| Recurrence model | Interval since last done. One open task at a time; no overdue pile-up |
| Activity types | Fixed, garden-flavoured enum |
| Season handling | Optional per-rule active window (month/day), wrap-around supported |
| Category | Typed enum on the area |
| Rule targets | Beds **and** areas, from day one |
| Task materialisation | Daily `@Scheduled` job |
| Map polygon | Column and API carry `boundary_json`; no client draws it this round |
| Clients | Backend, web, and Android in this round |

### Why `GardenArea` and not `Location`

`TrayLocation` already exists as a backend entity and resource, as
`web/src/pages/TrayLocations.tsx`, and as the Android `ui/location/` package.
A second `Location` would be ambiguous in every layer. `GardenArea` reads as a
sibling of `Bed` under `Garden` and can never be misread. The Swedish UI label
is unaffected.

## Domain model and schema

Three migrations, following the shape of `V27__bed_event.sql` and
`V40__bed_photo.sql`.

### V42 — `garden_area`

```sql
CREATE TABLE garden_area (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    garden_id     BIGINT      NOT NULL REFERENCES garden(id) ON DELETE CASCADE,
    name          VARCHAR(255) NOT NULL,
    description   TEXT,
    category      VARCHAR(32)  NOT NULL,
    boundary_json TEXT,
    size_sqm      DOUBLE PRECISION,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_garden_area_garden ON garden_area(garden_id);
```

`category` values: `WALKWAY`, `LAWN`, `HEDGE`, `COMPOST`, `GREENHOUSE`,
`WATER_FEATURE`, `STRUCTURE`, `OTHER`.

Org scoping goes through `garden.org_id`, exactly as `bed` does. There is no
`org_id` column on `garden_area`.

### V43 — `garden_area_event` and `garden_area_photo`

```sql
CREATE TABLE garden_area_event (
    id             BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    garden_area_id BIGINT      NOT NULL REFERENCES garden_area(id) ON DELETE CASCADE,
    event_type     VARCHAR(32) NOT NULL,
    event_date     DATE        NOT NULL,
    notes          TEXT,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_garden_area_event_area
    ON garden_area_event(garden_area_id, event_date DESC);
```

`garden_area_photo` mirrors `bed_photo` field for field, including `reason`,
`description` and `captured_at`, with `garden_area_id` in place of `bed_id`.

`garden_area_event.event_type` stores the `MaintenanceActivity` value directly,
plus `NOTE`. No parallel past-tense enum is invented for areas, and there is no
`PHOTO` event type — photos live in `garden_area_photo`, as they do for beds.

### V44 — `maintenance_rule` and `scheduled_task` columns

```sql
CREATE TABLE maintenance_rule (
    id                 BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    org_id             BIGINT      NOT NULL REFERENCES organization(id) ON DELETE CASCADE,
    bed_id             BIGINT      REFERENCES bed(id) ON DELETE CASCADE,
    garden_area_id     BIGINT      REFERENCES garden_area(id) ON DELETE CASCADE,
    activity_type      VARCHAR(32) NOT NULL,
    interval_days      INT         NOT NULL CHECK (interval_days >= 1),
    anchor_date        DATE,
    season_start_month SMALLINT, season_start_day SMALLINT,
    season_end_month   SMALLINT, season_end_day   SMALLINT,
    active             BOOLEAN     NOT NULL DEFAULT true,
    notes              TEXT,
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT maintenance_rule_one_target CHECK (
        (bed_id IS NOT NULL)::int + (garden_area_id IS NOT NULL)::int = 1
    ),
    CONSTRAINT maintenance_rule_season_all_or_none CHECK (
        num_nonnulls(season_start_month, season_start_day,
                     season_end_month, season_end_day) IN (0, 4)
    )
);

ALTER TABLE scheduled_task
    ADD COLUMN garden_area_id      BIGINT REFERENCES garden_area(id) ON DELETE CASCADE,
    ADD COLUMN maintenance_rule_id BIGINT REFERENCES maintenance_rule(id) ON DELETE SET NULL;

CREATE UNIQUE INDEX idx_scheduled_task_open_rule
    ON scheduled_task(maintenance_rule_id)
    WHERE maintenance_rule_id IS NOT NULL AND status = 'PENDING';
```

Two nullable foreign keys with a check constraint, rather than a generic
`target_type`/`target_id` pair: just as polymorphic, but real referential
integrity and real cascade deletes.

Season bounds are month/day pairs rather than dates so the window repeats every
year. Wrap-around windows are supported: `Nov 1 – Mar 31` for snow clearing
behaves the same as `Apr 1 – Oct 15` for weeding.

### `MaintenanceActivity`

One Kotlin enum, carrying which target types accept each activity and how it
maps onto the existing bed event log.

| Activity | Beds | Areas | Bed event type |
|---|---|---|---|
| `WATER` | yes | yes | `WATERED` |
| `WEED` | yes | yes | `WEEDED` |
| `FERTILIZE` | yes | no | `APPLIED_SUPPLY` |
| `MOW` | no | yes | — |
| `RAKE` | no | yes | — |
| `PRUNE` | no | yes | — |
| `EDGE` | no | yes | — |
| `SWEEP` | no | yes | — |
| `TOP_UP` | no | yes | — |
| `CLEAN` | no | yes | — |
| `INSPECT` | no | yes | — |

Bed rules are restricted to activities with a `PlantEventType` equivalent, so
existing bed history stays coherent.

## The maintenance engine

### Last-done is derived, not stamped

A `last_completed_at` column on the rule would mean that weeding the path and
logging it the normal way leaves the reminder still nagging. Instead each
activity declares where its history lives:

| Activity | Source of last-done |
|---|---|
| `WEED` / `WATER` on a bed | `bed_event` where `event_type` is `WEEDED` / `WATERED` — the rows `PlantService.weedBed` / `waterBed` already write |
| `FERTILIZE` on a bed | latest of `supply_application` joined to `supply_type.category = 'FERTILIZER'`, or `bed_event` with `APPLIED_SUPPLY` |
| any activity on an area | `garden_area_event` where `event_type` equals the activity |

The `FERTILIZE` row needs both sources because bed fertilising is recorded in
`supply_application.bed_id`, not in `bed_event`. Without the first source the
clock would never move and the task would regenerate immediately.

### Due date

```
lastDone = max(rule.anchor_date, latest matching event)   -- both nullable
due      = lastDone + interval_days                       -- null lastDone means due now
if a season window exists and `due` falls outside it:
    due = the window's next opening on or after `due`
```

`anchor_date` is an optional "I last did this on…" captured when creating the
rule. Leaving it blank makes the rule due immediately, subject to its window.

Because "next opening" is computed from the month/day pair rather than a date
range, wrap-around windows need no special case.

### The daily job

`MaintenanceScheduler`, `@Scheduled(cron = "0 30 3 * * ?")`, sitting alongside
the two existing weather jobs in `WeatherIngestionService`:

1. Load active rules.
2. Skip any rule that already has a `PENDING` task.
3. Compute `due`; if `due <= today`, insert one `ScheduledTask` with
   `targetCount = 1`, `earliestDate = deadline = due`, carrying
   `maintenance_rule_id` and the rule's `bed_id` or `garden_area_id`.

The partial unique index makes the job idempotent by construction: a double
run, a retry, or a manual trigger cannot produce duplicates.

### Completion

Completion goes through the existing `ScheduledTaskService.completePartially`.
When a task carrying a `maintenance_rule_id` reaches zero remaining, the
service writes the corresponding event row. For beds this goes through the same
`weedBed` / `waterBed` path the button uses, so a completed task and a tapped
button are indistinguishable in bed history. For `FERTILIZE`, completion writes
a `bed_event` with `APPLIED_SUPPLY` (quantities are unknown, so no
`supply_application` row is fabricated).

The derived clock then moves and the next task appears one interval later.
Nothing chains synchronously; the job is the only creator of rule-backed tasks.

### Edits, deactivation, deletion

- Changing `interval_days` recomputes the next due from `lastDone`. An already
  open task is left alone.
- `active = false` stops generation but does not delete the open task.
- Deleting a rule leaves any in-flight task orphaned but usable
  (`ON DELETE SET NULL`).

### Existing validation

`ScheduledTaskService.BED_ACTIVITY_TYPES` is currently the hardcoded
`setOf("WATER", "FERTILIZE", "WEED")`. It should derive from
`MaintenanceActivity` instead, with an area equivalent added, so manually
created area tasks validate the same way.

## API

`GardenAreaResource` and `MaintenanceRuleResource`, following `BedResource`'s
`@Path("/api")` plus `OrgContext` style.

```
GET  POST        /api/gardens/{gardenId}/areas
GET  PUT  DELETE /api/areas/{id}
GET  POST        /api/areas/{id}/events        -- direct logging and history
GET  POST        /api/areas/{id}/photos
DELETE           /api/areas/{id}/photos/{photoId}

GET  POST        /api/maintenance-rules?bedId=&areaId=
PUT  DELETE      /api/maintenance-rules/{id}
```

Nested create plus flat detail matches `/api/gardens/{id}/beds` and
`/api/beds/{id}`.

On `GET /api/maintenance-rules`, both query parameters are optional and at most
one may be supplied: `bedId` lists that bed's rules, `areaId` lists that area's,
and neither lists every rule in the org. Supplying both is a 400.

One deliberate departure from the bed precedent: beds expose verb endpoints
(`POST /api/beds/{id}/weed`, `/water`). With ten activities that does not
scale, so areas get one generic `POST /api/areas/{id}/events` taking
`{activityType, eventDate, notes}`. The existing bed verb endpoints are
untouched.

`ScheduledTaskResponse` gains `gardenAreaId`, `gardenAreaName`, and
`maintenanceRuleId`.

`ApiContractTest` should pin `ScheduledTaskResponse` (currently unpinned) plus
the new response DTOs, since three clients hand-type these.

## Out of scope

- Drawing or rendering polygons. `boundary_json` is carried by the schema and
  API; no client draws it this round. A standalone polygon editor — which would
  also fix the fact that a bed created outside the garden wizard can never get a
  shape — is its own piece of work.
- Seeding default rules per category. Rules are created by hand.
- Any change to the existing bed verb endpoints or the garden creation wizard.

## Risks and phasing

This is a large change: three migrations, two new backend resources with
services and repositories, four to five new web pages and components, a new
Android UI package, and both i18n files plus both `strings.xml`. The
implementation plan should order it in phases that are each verifiable on their
own: **backend first**, then **web**, then **Android**.

Wiring beds into the rule engine changes existing behaviour — beds that today
only ever get hand-made tasks will start generating them. That is intended, but
it is the part most likely to surprise in use, so **bed rules ship
off-by-default**: no rules are seeded and nothing changes until one is created.
